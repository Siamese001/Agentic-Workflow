## 3. Manual Command

Operators run the advisory gate weekly with:

```powershell
python ops_scripts/ci/check_runtime_certification.py `
    --repo-root . `
    --baseline docs/reference/runtime_certification/cert_baseline.toml
```

(POSIX-equivalent uses backslash continuations or a single-line form.)

### 3.1 Optional flags

| Flag | Effect |
|---|---|
| `--report <path>` | Write a JSON report to `<path>` (e.g., `docs/reports/runtime_cert/phase_e_runs/2026-W18.json`). Not authored by default; this report is Markdown-only |
| `--strict` | Requests strict exit-code translation. **Downgraded to advisory** by the baseline's `mode="advisory"` field; emits `WARNING_STRICT_DOWNGRADED_BY_BASELINE`. CLI exit remains `0` |

### 3.2 Operator environment

- Python 3.11+ (stdlib `tomllib`); fallback to `tomli` is supported
- No network or subprocess dependencies
- No write access to `artifacts/ledgers/` is required — the gate reads the per-app ledger SQLite files only

## 4. Expected Advisory Behavior

The four ledger-state outcomes the operator may observe in week one and beyond:

| # | Ledger state | `result.passed` | `app_results[0].failures` | `app_results[0].warnings` | CLI exit |
|---|---|---|---|---|---:|
| 1 | No `artifacts/ledgers/cert_decision_apps_research.sqlite` | `False` | `("LEDGER_MISSING",)` | `()` | `0` |
| 2 | Ledger present but contains zero rows (`require_ledger=true`) | `False` | `("LEDGER_EMPTY",)` | `()` | `0` |
| 3 | Latest row `verdict="reject"` | `False` | `("LATEST_DECISION_BELOW_BASELINE",)` | `()` | `0` |
| 4 | Latest row `verdict="hold"` or `verdict="certify"` | `True` | `()` | `()` | `0` |

In all four cases:

- `result.runtime_certification_status == "NOT_CERTIFIED"`
- `result.disclaimer` contains the phrase `"no runtime certification performed"`
- `result.checked_apps == 1`
- `result.advisory == True`
- `result.mode == "advisory"`
- When `failure_count > 0`, the gate emits `WARNING_ADVISORY_FAILURES_SUPPRESSED` at the gate level

### 4.1 Critical non-promotion property (case 4)

> A latest ledger `verdict == "certify"` that meets the baseline
> `min_verdict` is **still non-promoting**. The gate marks the app
> `passed=True`, but `result.runtime_certification_status` remains
> `"NOT_CERTIFIED"`. Every cert-decision row the gate reads also carries
> `runtime_certification_status_before = NOT_CERTIFIED` and
> `runtime_certification_status_after = NOT_CERTIFIED` — enforced by D.1
> `__post_init__`, D.3 SQL `CHECK`, D.3 read-back `_hydrate_one`, and
> D.4 smoke `__post_init__`. The gate's `passed=True` is a consistency
> signal, not a certification signal.

#### 4.3.2 Invocation note — PYTHONPATH

The direct script invocation

```powershell
python ops_scripts/ci/check_runtime_certification.py `
    --repo-root . `
    --baseline docs/reference/runtime_certification/cert_baseline.toml
```

initially failed with:

```
ModuleNotFoundError: No module named 'tools'
```

Root cause: `ops_scripts/ci/check_runtime_certification.py` imports
`tools.runtime_cert.decisions.*`, but running the file as a script
does not place the repo root on `sys.path`. Successful invocation used
an explicit `PYTHONPATH`:

```powershell
$env:PYTHONPATH = "."
python ops_scripts/ci/check_runtime_certification.py `
    --repo-root . `
    --baseline docs/reference/runtime_certification/cert_baseline.toml
```

This is an **operator-UX issue, not a gate-correctness issue.** Gate
behavior, non-promotion invariants, and all 36 E1.W2 unit tests are
unaffected (tests invoke the module via import, which resolves
correctly). A two-line `sys.path` bootstrap at the top of the CLI
module would remove the need for `PYTHONPATH=.`, but that edit modifies
a Phase E.1 shipped module and is **deferred to E1.W3.1 under a
separate scoped prompt**. This report does not authorize that change.

## 5. No-Certification Disclaimer

> **No runtime certification was performed by this report or by the
> Phase E.1 advisory gate.**
>
> The gate is read-only. It loads the TOML baseline, reads the per-app
> Phase D cert-decision ledgers, and emits a structured advisory result.
> It writes no certification state, mutates no ledger, and modifies no
> scanner bucket. Every `RuntimeCertGateResult` it constructs has
> `runtime_certification_status = "NOT_CERTIFIED"` — enforced
> structurally via `RuntimeCertGateResult.__post_init__` (raises on any
> other value). Every cert-decision row the gate reads back is
> re-validated by D.3's `_hydrate_one` (which invokes D.1's
> `__post_init__` plus the `compute_decision_id` tamper check), so
> tampered rows surface as `LEDGER_READ_ERROR` rather than promoting any
> app.
>
> The gate's CLI exit code is a build signal, not a certification
> signal. Advisory mode always exits `0`. Strict mode (when eventually
> enabled in E1.W4 under its own Author-Gate) exits `0` / `1` / `2` for
> pass / app-failure / gate-abstain. None of these exit codes promotes
> any app.
>
> `runtime_certification_status` for every app remains `NOT_CERTIFIED`
> end-to-end through Phase E.1.

## 6. Known Blocker (Week One)

**If no `artifacts/ledgers/cert_decision_apps_research.sqlite` ledger
file exists yet, the advisory gate reports `LEDGER_MISSING` but the CLI
exits `0`.** This is expected behavior under §4 case 1 and §5
non-certification invariants.

The week-one observation is **honest non-green** — the same pattern as
the Phase D.5 closeout report (which also documented an absent C.6
live-run state at that time). Honest non-green is a feature, not a
defect:

- The advisory gate's job is to surface evidence gaps without blocking
  development.
- Forcing the gate to pass would require either lying in the baseline
  (`require_ledger=false`, which masks the data gap) or fabricating a
  ledger row (which violates §5 non-certification invariants).
- The correct response is to leave the gate honest and address the data
  gap in subsequent weeks via §7.

## 8. Phase E / Phase F Boundary

> ⛔ **E1.W3 does not wire CI.** No `.pre-commit-config.yaml` edit. No
> `.github/workflows/` edit. The advisory gate is invokable only by an
> operator running the §3 manual command.

> ⛔ **E1.W4 owns the advisory-to-strict CI discussion.** Flipping the
> baseline's `mode` field to `"strict_allowed"`, wiring the gate into
> pre-commit, or wiring it into a CI workflow all require the separate
> E1.W4 Author-Gate. The graduation criterion is **4 consecutive clean
> advisory weeks plus zero unresolved false positives** per E-AG-5.

> ⛔ **Phase F owns scanner promotion and `runtime_mode` bucket
> changes.** Recognition of `RUNTIME_CERTIFIED` /
> `FORMAL_EXCEPTION_VERIFIED` buckets, scanner bucket extension, and
> any actual promotion of an app from `NOT_CERTIFIED` to a certified
> status are entirely Phase F scope. Phase E.1 (this waveline) feeds
> Phase F with read-only evidence; Phase F decides and acts under its
> own separate Author-Gate.

This boundary is structurally enforced:

- E1.W2 gate's `RuntimeCertGateResult.__post_init__` raises on any
  `runtime_certification_status ≠ NOT_CERTIFIED`
- D.1 / D.3 `CHECK` constraints reject any cert-decision row with a
  non-`NOT_CERTIFIED` status field
- E1.W2 gate has no scanner / emitter / app-package imports (audited by
  test); the gate cannot, by construction, mutate scanner state
- The baseline TOML's `expected_runtime_certification_status` field is
  pinned to `"NOT_CERTIFIED"` and validated via
  `BASELINE_APP_INVALID` on any other value
