## 2. Triple/Quintuple Non-Promotion Guarantee

Five independent layers each capable of rejecting a non-compliant row:

1. **C.8 input** — `PhaseCCloseoutReport.__post_init__` rejects any status other than `NOT_CERTIFIED` before D.2 ever sees the report
2. **D.1 construction** — `CertificationDecisionRecord.__post_init__` rejects any record whose `_before` or `_after` status is not `NOT_CERTIFIED`
3. **D.3 SQL CHECK** — `CHECK (runtime_certification_status_before = 'NOT_CERTIFIED')` + `CHECK (runtime_certification_status_after = 'NOT_CERTIFIED')` in `.windsurf/schemas/cert_decision_ledger.schema.sql`
4. **D.3 read-back** — `_hydrate_one` re-runs D.1's `__post_init__` on every row AND re-computes `compute_decision_id` to reject direct SQL tamper
5. **D.4 smoke report** — `CertDecisionSmokeReport.__post_init__` pins `runtime_certification_status == NOT_CERTIFIED`, pins `schema_version == "d4-smoke-v1"`, pins the disclaimer phrase, verifies every read-back row carries `NOT_CERTIFIED` on both status columns

Corrupting any one layer still leaves four others standing. See §9 for the full layer-by-layer table.

## 3. D.1 — `CertificationDecisionRecord` Schema

- **Module**: `tools/runtime_cert/decisions/cert_decision_record.py`
- **Planning artifact**: implemented as part of the Phase D design in ADR-080 §5; no dedicated D.1 Author-Gate plan (schema-only, inside ADR-080 scope)

### Public surface

| Symbol | Kind | Purpose |
|---|---|---|
| `CertificationDecisionRecord` | frozen dataclass, 19 fields | Canonical Phase D decision record |
| `NOT_CERTIFIED` | `str` constant | Only allowed value for `runtime_certification_status_before` / `_after` |
| `VERDICT_CERTIFY` / `VERDICT_HOLD` / `VERDICT_REJECT` | `str` constants | Closed verdict set |
| `EVIDENCE_KIND_R3` / `_BTC` / `_FORMAL_EXCEPTION` / `_SKIPPED` | `str` constants | Closed evidence-kind set |
| `compute_decision_id(app_name, manifest_hash, closeout_report_hash)` | function | Deterministic SHA-256 hex over the three inputs |
| `make_certification_decision_record(...)` | constructor helper | Hydrates a record and computes `decision_id` internally |
| `CertificationDecisionRecord.to_dict()` / `.to_json()` | methods | JSON-safe serialization; `failure_reasons` tuple → list; sorted-key compact JSON |

### Invariants enforced at construction (excerpted from `__post_init__`)

- `runtime_certification_status_before == _after == NOT_CERTIFIED`
- `0 <= trace_observed_success_n <= trace_observed_n`
- `0.0 <= evidence_rate <= 1.0`; `0.0 <= wilson_lower <= 1.0`
- `z_score` and `uplift` are finite floats (no NaN, no inf)
- `decision_id` is exactly 64 lowercase hex chars AND equal to `compute_decision_id(app_name, manifest_hash, closeout_report_hash)`
- `verdict ∈ {VERDICT_CERTIFY, VERDICT_HOLD, VERDICT_REJECT}` — closed set
- `failure_reasons` is a tuple with entries drawn from a closed ontology
- `generated_at_utc` and `next_review_utc` are ISO-8601 UTC strings

### Hard rule

**Schema only. No business logic. No I/O. No ledger writes. No runtime promotion.** D.1 is a type + its construction guard; any higher-level concern is D.2's or D.3's responsibility.

## 4. D.2 — Closeout-to-Decision Evaluator

- **Module**: `tools/runtime_cert/decisions/cert_decision_evaluator.py`
- **Planning artifact**: `.windsurf/plans/runtime-cert-d2-decision-evaluator-227b38.md`

### Public surface

| Symbol | Signature / meaning |
|---|---|
| `evaluate_phase_c_closeout` | `(report: PhaseCCloseoutReport, history: Iterable[CertificationDecisionRecord] = (), *, closeout_report_id: str | None = None, closeout_report_hash: str | None = None) -> tuple[CertificationDecisionRecord, ...]` |
| `wilson_lower_bound` | `(successes: int, n: int, z: float = 1.96) -> float` — local stdlib helper |
| `derive_closeout_report_hash` | `(report: PhaseCCloseoutReport) -> str` — deterministic SHA-256 over canonical-JSON `report.to_dict()`; no filesystem read |

### Closed 12-reason failure ontology

`CLOSEOUT_MISSING`, `SAMPLE_SIZE_TOO_SMALL`, `WILSON_BELOW_THRESHOLD`, `Z_SCORE_BELOW_THRESHOLD`, `UPLIFT_NOT_POSITIVE`, `CRITICAL_BLOCKERS_PRESENT`, `FORBIDDEN_SPAN_VIOLATION`, `FORMAL_CONTROL_MISSING_OR_FAILED`, `MANIFEST_HASH_DRIFT`, `AMBIGUOUS_EVIDENCE`, `NOT_TRACE_OBSERVED_READY`, `NOT_FORMAL_EXCEPTION_OBSERVED_READY`.

### Thresholds (ADR-080 §7)

- `MIN_N = 30`
- `MIN_WILSON_LOWER = 0.60`
- `MIN_Z_SCORE = 1.96`
- `MIN_UPLIFT = 0.0` (strict inequality)
- Review cadences: 30 days for `certify`, 7 days for `hold`, 7 days for `reject`

### Verdict semantics (load-bearing)

A `verdict == "certify"` result is **not** a certification. The evaluator reports what a hypothetical Phase F promoter *would* do if it existed; it does not promote anything itself. Every produced record carries `runtime_certification_status_after = NOT_CERTIFIED`, structurally enforced by D.1's `__post_init__`.

### Purity

Verified by `test_no_filesystem_or_sqlite_access` — the test patches `builtins.open` and `sqlite3.connect` to raise, then runs the evaluator through all three verdict branches; no `open` or `sqlite3.connect` call is ever attempted.

### Hard rule

**Pure. No I/O. No sqlite. No subprocess. No ledger writes.**

## 5. D.3 — Cert-Decision Ledger Writer

- **Module**: `tools/runtime_cert/decisions/cert_decision_ledger.py`
- **DDL**: `.windsurf/schemas/cert_decision_ledger.schema.sql` (21 columns, 3 indexes, 2 `CHECK` constraints)
- **Planning artifact**: `.windsurf/plans/runtime-cert-d3-cert-decision-ledger-85989c.md`

### Public surface

| Symbol | Purpose |
|---|---|
| `CertDecisionLedgerWriteResult` | Frozen dataclass; exactly one of `written` / `already_exists` / `skipped` is `True`; `error` non-empty iff `skipped=True` |
| `ledger_path_for_app(app_name, *, repo_root=None)` | Returns `<repo_root>/artifacts/ledgers/cert_decision_<app_name>.sqlite` |
| `ensure_cert_decision_ledger(path)` | Idempotently creates parent dir + applies DDL (all `IF NOT EXISTS`) |
| `write_cert_decision_record(record, *, repo_root=None, fail_soft=True)` | Persists one record; idempotent on `decision_id` |
| `read_cert_decision_records(app_name, *, repo_root=None)` | Returns `tuple[CertificationDecisionRecord, ...]` ordered by `generated_at_utc` ASC, tie-broken by `decision_id` |

### Ledger layout

**Per-app SQLite files**, one per app:

```
<repo_root>/artifacts/ledgers/cert_decision_<app_name>.sqlite
```

This is deliberately **not** a shared ledger. Each app has its own file; cross-app write contention is impossible.

### Idempotency

`INSERT OR IGNORE` on the `decision_id` primary key, combined with a `total_changes == 0` check:

- If the insert succeeds → `written=True`
- If the insert is ignored because the row exists → `already_exists=True`
- If a `sqlite3.Error` fires in `fail_soft=True` mode → `skipped=True, error="<message>"`

### Tamper detection on read-back

`_hydrate_one(record_json)` does three things for every row:

1. Parses `record_json` via `json.loads`
2. Re-runs the full D.1 `CertificationDecisionRecord(**d)` construction, which triggers D.1's `__post_init__`
3. Re-computes `compute_decision_id(app_name, manifest_hash, closeout_report_hash)` and compares to the row's stored `decision_id`

Any direct SQL `UPDATE` to the status columns, `record_json`, or `decision_id` surfaces as a `ValueError` on read.

### Registry discipline (ADR-050 cross-reference)

**D.3's DDL is deliberately NOT registered in `tools/ledgers/schema_registry.py` LEDGER_REGISTRY.** `tools/ledgers/apply_schema.py` iterates the registry only, so it will never auto-apply the D.3 DDL alongside the intelligence-ledger family. This is intentional and verified by `test_ddl_not_registered_in_ledger_registry`.

Rationale (recorded in the D.3 plan):

- The cert-decision ledger is per-app, not singleton; the registry pattern assumes one file per registered name
- Idempotency is keyed on `decision_id` (domain-specific), not on the generic hash used by `tools.ledgers.writer`
- The D.3 writer owns its own path resolution (`ledger_path_for_app`), its own DDL loader, and its own lock table

ADR-050 (`docs/architecture/adr/ADR-050-intelligence-ledger-family.md`) remains the reference for the intelligence-ledger family contract against which D.3 declined membership. Any future Phase E / Phase F integration that wants router-style `CERT_DECISION:` marker emission will re-evaluate that decision.

### Bypass

`CERT_DECISION_LEDGER_BYPASS=1` env var — same shape as the other constitutional bypass mechanisms. When set, `write_cert_decision_record` returns a `skipped=True` result without touching disk.

### Hard rule

**Persistent writer. No scanner promotion. No CI gate. No emitter touch.** Every persisted row carries `NOT_CERTIFIED` on both status columns verbatim, regardless of `verdict`.

## 11. Known Limitations

Recorded honestly so Phase E and Phase F planning starts with full context:

1. **No real-app dry-run evidence.** The D.4 smoke harness has not been exercised against a real C.8 closeout report outside pytest. That is an operator task and belongs to a later ad-hoc D-review, not to D.5.
2. **Thresholds are provisional.** ADR-080 §12 Q2 and Q3 remain deferred to D.5 calibration. The `MIN_N=30 / MIN_WILSON_LOWER=0.60 / MIN_Z_SCORE=1.96` floor is drawn from calibration-report precedent (`intelligence-ledger-family.md` §5) but has not been validated against a real Phase D cohort. Any Phase F promotion cycle should re-calibrate against observed app behavior before trusting these defaults.
3. **`uplift` baseline uses the most-recent prior for the same app regardless of `manifest_hash`.** That is a deliberate D.2 choice (captured in the D.2 plan); it means manifest-drifted history dilutes baseline signal. Calibration to watch for.
4. **No router-event emission.** Constitutional rule §29 requires `ROUTER_DECISION:` markers for routing decisions. Phase D is not a router but **is** a decision pipeline. ADR-080 §6 mentions a possible `CERT_DECISION:` marker per decision. D.3 does **not** emit such a marker today; D.4 does **not** either. Whether to add one is an open design question deferred beyond Phase D — it surfaces naturally in Phase E or Phase F planning if the operational need arises.
5. **No ledger-rotation / archival policy.** Per-app SQLite files grow forever. Not a D.5 concern, but documented for Phase E/F operational planning.
6. **No cross-process locking.** D.3 uses an in-process `threading.Lock` keyed on `db_path`. Two processes writing the same ledger file race at the SQLite layer; `INSERT OR IGNORE` absorbs duplicates but other transient errors fall through to `fail_soft`. Documented; not a D.5 code change.
7. **Attribution anomaly in the D.5 plan commit.** `.windsurf/plans/runtime-cert-d5-phase-d-closeout-5e9d2a.md` was committed inside `e9a594c3756a7eab68ee9ac109bb8f11650f4d8a`, whose subject is `docs(rtc-w2b): P9 W2b report + W2 status link-forward`. The plan content is unaffected and byte-identical to the authoring; history was not rewritten. Future references should use the path + SHA pair, not the commit subject.

None of these block Phase E planning. All of them are known and documented.
