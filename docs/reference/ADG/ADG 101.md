================================================================================
0.A. GRAPH THEORY BASICS (The Vocabulary)
================================================================================
Before navigating an ADG, you must understand the primitives of Graph Theory.
A Graph is a mathematical structure used to model pairwise relations between objects.

  * NODE (Vertex): An entity or object (e.g., a File, a Function, a Layer).
  * EDGE (Link/Relation): The connection between two nodes (e.g., "imports").
  * DIRECTED EDGE: A connection with a specific direction (A -> B).
  * PATH: A sequence of edges connecting a sequence of nodes.

     [ NODE A ] ======== DIRECTED EDGE =======> [ NODE B ]
     (Source)           "flows_to"              (Target)


================================================================================
0.B. WHAT IS AN ADG (Automated Dependency Graph)?
================================================================================
An ADG is a specialized graph that maps the total architecture of a software
system. Instead of just showing raw text, it extracts and maps:
  1. What the code IS (Modules, Files, Classes).
  2. What the code DOES (Functions, Symbols, Data Flows).
  3. What the code MUST OBEY (Policies, Layers, Architectural Rules).
  4. What boundaries the code CROSSES (Execution, Security, Write Surfaces).

It "Automates" the discovery of these dependencies so agents or developers can
reason about system impact programmatically across millions of lines of code.
To do this, it relies on an underlying Abstract Syntax Tree (AST) extraction pipeline.


================================================================================
0.C. THE AST MENTAL MODEL & EXTRACTION PIPELINE
================================================================================
The AST represents the syntax tree of code. Dependency Graphs are different
projections extracted from that tree, split across two axes:

  * STATIC STRUCTURE AXIS: Import Graph, Class Inheritance Graph, Module /
    Component Graph, Symbol / Attribute Graph, Object Composition Graph.
  * DYNAMIC EXECUTION AXIS: Function Call Graph.

[ Source Code Files ]
        │
        ▼
[ AST Parser ]
        │
        ▼
[ AST Nodes Extracted ]
        │
        ├─ Import / ImportFrom      → builds IMPORT GRAPH
        ├─ Call()                   → builds FUNCTION CALL GRAPH
        ├─ ClassDef + bases         → builds CLASS INHERITANCE GRAPH
        ├─ Name() / Attribute()     → builds SYMBOL / ATTRIBUTE GRAPH
        ├─ Assign() + constructor   → builds OBJECT COMPOSITION GRAPH
        └─ module grouping          → builds MODULE / COMPONENT GRAPH
        │
        ▼
[ Edge Extraction Rules ]
        │
        ▼
[ Dependency Graph Family (The Building Blocks of the ADG) ]

0.E. THE TOPOLOGICAL PROBLEM & ADG FLOWCHARTS
================================================================================
PROBLEM: How do we accurately calculate the deterministic blast radius of a
high-level architectural violation (e.g., a Layer policy breach) down to the
granular execution level, while identifying if that flow hits critical
vulnerability surfaces?

Direct mapping fails due to namespace isolation: policy layers, file imports,
and execution symbols exist in different topologies with no shared edges.

SOLUTION: An ADG flowchart is a topological map that resolves these node-type
mismatches. It models deterministic relationships across disparate semantic
boundaries, visualizing the intersection of static environmental metadata
(policy rules) with runtime logic (symbol-level data flow hitting surfaces).


================================================================================
0.F. THE FIVE ADG SURFACES (Risk & Action Boundaries)
================================================================================
Surfaces are semantic boundaries within the ADG ("World 3: Symbols") that track
how untrusted inputs flow through the application. Identifying these nodes is
critical for tracing code injection, state corruption, policy bypasses, and
data exfiltration.

  1. EXECUTION SURFACE: Where static data transitions into active computation
     (e.g., invokes_eval, calls). Maps expected paths and highlights Arbitrary
     Code Execution (ACE) risks.

  2. WRITE SURFACE: Where execution mutates system state (e.g., writes_to).
     Crucial for tracking side-effects, idempotency, and data corruption risks.

  3. GOVERNANCE SURFACE: Where enterprise rules and policies are enforced
     (e.g., applies_guardrail, requires_human_review). The safety boundary
     that prevents autonomous execution of high-risk tasks.

  4. DETERMINISM SURFACE: Where execution relies on runtime signals (e.g.,
     uses_wall_clock, seeds_rng). Operations crossing this limit complicate
     debugging, reproducibility, and caching.

  5. SECURITY SURFACE: Where the system interacts with restricted info or
     external networks (e.g., reads_secret, external_http_call). The absolute
     trust limit and prime target for exfiltration.

1. THE TYPE GAP & THE INTEGRATED SURFACES (Why Direct Joins Fail)
================================================================================
You have three distinct topologies powered by different underlying AST graphs.
They do not naturally overlap because their nodes are fundamentally different types.
Furthermore, ADG Surfaces act as hard boundaries within the Symbol topology that
dictate risk.

  [ WORLD 1: VIOLATIONS ]     [ WORLD 2: IMPORTS ]       [ WORLD 3: SYMBOLS & SURFACES ]
  (Policy & Governance)       (Import/Module Graphs)     (Call/Symbol Graphs & Risks)

2. THE BRIDGE (Resolving the Type Mismatch to Map Surface Exposure)
================================================================================
To cross the domains, you must use the OWNERSHIP edge. Modules contain Symbols.
This is the only legal pathway from the Violation space (World 1) through the
Import structure (World 2) to the Symbol space (World 3) to determine which
Risk Surfaces are exposed.

                           ( The Missing Link )
  [ Module_Y ] -------------------owns-------------------> [ Symbol_Y1 ]
       |                                                        |
    imports                                                  flows_to (Active Computation)
       v                                                        v
  [ Module_X ] -------------------owns-------------------> [ EXECUTION SURFACE: calls ]
       |                                                        |
    imports                                                  flows_to (Sensitive Access)
       v                                                        v
  [ Module_A ] -------------------owns-------------------> [ SECURITY SURFACE: reads_secret ]
       |                                                        |
    violates                                                 flows_to (State Mutation)
       v                                                        v
  [ Layer_L5 ]                                             [ WRITE SURFACE: writes_to ]

3. THE DIRECTIONAL RULE (Forward vs. Reverse)
================================================================================
When tracing the Import graph, your direction dictates the question you answer.
For violations, you MUST walk in reverse to find the downstream impact.

  FORWARD WALK (Dependency View)          REVERSE WALK (Blast-Radius View)
  "What do I need to run?"                "Who do I break if I change?"

  [ Module_Y ]                            [ Module_Y ]
       |                                       ^
       | (Step 1)                              | (Step 2: Who uses X?)
       v                                       |
  [ Module_X ]                            [ Module_X ]
       |                                       ^
       | (Step 2)                              | (Step 1: Who uses A?)
       v                                       |
  [ Module_A ]                            [ Module_A ] <--- START HERE
