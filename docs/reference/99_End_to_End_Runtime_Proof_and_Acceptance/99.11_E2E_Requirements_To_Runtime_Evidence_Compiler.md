1. PURPOSE
------------------------------------------------------------------------------------------------------------------------
This file defines the **executable contract** for the E2E Requirements-to-Runtime-Evidence Compiler. The compiler is the
single tool that converts the requirements pack (markdown REQ_ID rows) into a deterministic, fail-closed report bundle
that the release gate consumes.

The compiler exists to make this claim impossible:
> "pytest passed and full proof passed, therefore architecture is proven."

The compiler exists to force this claim:
> "Every applicable REQ_ID has mapped runtime artifact evidence, OTEL span evidence, validator evidence, negative-control
>  evidence with `expected_fail_reason`, replay evidence, and release-gate `PASS` (or `NOT_APPLICABLE` with reason)."

This file uniquely owns:
- the compiler input contract
- the markdown REQ_ID extraction algorithm
- the runtime evidence discovery algorithm
- the per-row status computation rules
- the anti-cheat detectors and their contract
- the report bundle schema (10 reports)
- the release-blocking decision rule
- the deterministic-replay obligation for the compiler itself

This file does **not** own:
- the REQ_ID grammar or namespace map (`00X` §3, §3.1)
- the status / evidence / fail-reason vocabularies (`00X` §5, §6)
- the no-overlap law (`00X` §9)
- per-layer atomic REQ_IDs (each layer pack)

- The compiler MUST NOT accept "test passed" as evidence without REQ_ID linkage.

**Allowed outputs only**:
- Read-only reports listed above
- A single boolean `release_blocking` flag for the gate
- A deterministic compiler digest

5. RUNTIME EVIDENCE CONTRACT
------------------------------------------------------------------------------------------------------------------------
The compiler emits `compiler_run.json` with these fields:
- `compiler_run_id` (uuid4)
- `started_at_utc`, `finished_at_utc`
- `rule_source_sha256` (sha256 of `00X.md`)
- `inputs.markdown_files_count`
- `inputs.runtime_artifacts_count`
- `inputs.otel_traces_count`
- `inputs.validator_receipts_count`
- `inputs.replay_receipts_count`
- `outputs.bundle_sha256`
- `outputs.release_blocking` (boolean)
- `outputs.row_count`
- `outputs.row_count_by_status` (map)
- `outputs.anti_cheat_findings_count`

Each compiler-emitted artifact MUST carry:
- `req_id` (the row this artifact substantiates) — `MULTIPLE` allowed for index files
- `trace_id` (compiler's own run trace)
- `policy_hash` (the `00X` rule source hash)
- `blueprint_hash` (the compiler version + config hash)
- `replay_key` (input set fingerprint)
- `content_hash` (sha256 of the artifact body)
- `lineage` (input artifact IDs that produced this output)

```
├── req_compiler.extract_markdown
├── req_compiler.scan_code
├── req_compiler.scan_tests
├── req_compiler.scan_artifacts
├── req_compiler.scan_otel
├── req_compiler.scan_validators
├── req_compiler.scan_replay
├── req_compiler.compute_status
├── req_compiler.run_anti_cheat
├── req_compiler.verify_otel_chain
├── req_compiler.verify_content_hash
├── req_compiler.verify_namespace
├── req_compiler.verify_uniqueness
├── req_compiler.nc_reason_match
├── req_compiler.emit_top25
├── req_compiler.emit_bundle
└── req_compiler.release_decision
```

Required attributes on `req_compiler.run`:
- `compiler_run_id`, `rule_source_sha256`, `bundle_sha256`, `release_blocking`, `row_count`

Required attributes on every child span:
- `req_compiler.phase` matching the span name suffix
- `inputs_count`, `outputs_count`
- `status_code` ∈ {`OK`, `ERROR`}
- On `ERROR`: `attributes.fail_reason_code`

Failure span behavior: any phase that fails sets the run span status to `ERROR` and propagates `fail_reason_code` to the run span attributes; downstream phases MUST NOT silently skip — they MUST emit `status_code=ERROR` with `attributes.fail_reason_code=upstream_phase_failed`.

Trace completeness expectation: a release-gate compiler trace MUST contain every span listed above. Missing any span renders the compiler run `UNVERIFIED`.

7. VALIDATOR CONTRACT
------------------------------------------------------------------------------------------------------------------------
Each validator listed in the table above is a Python module exposing `validate(input_path) -> ValidatorReceipt`.

`ValidatorReceipt` shape:
```
{
  "validator_name": str,
  "req_id": str | "MULTIPLE",
  "result": "pass" | "fail",
  "reason_code": str,
  "evidence_refs": [str, ...],
  "replay_refs": [str, ...],
  "details": {arbitrary, JSON-safe}
}
```

Validator scopes:
- `runtime` — runs during a live request flow (rare here; mostly compile-time CI / release-gate).
- `CI` — runs in CI on every push.
- `release-gate` — runs only when computing release decision; failure here is fail-closed.

The compiler MUST treat any validator that returns `result=fail` with empty `reason_code` as `FAKE` per `00X` §11.1.

8. NEGATIVE CONTROL CONTRACT
------------------------------------------------------------------------------------------------------------------------
Every negative control row in §4 has a `control_id` of the form `NC-COMPILER-<SEMANTIC-NAME>-<3-DIGIT-SEQ>`.

Each negative control:
1. Targets a single REQ_ID.
2. Attempts a specific tamper / bypass listed in the row's `Negative Control` cell.
3. Is expected to trip the row's validator with `reason_code` exactly equal to the row's `Expected Fail Reason`.
4. Produces a `nc_receipt` artifact with: `nc_id`, `target_req_id`, `tamper_kind`, `result` ∈ {`tripped`, `escaped`}, `reason_code`, `evidence_refs[]`.

Rule (binding):
- `result=tripped` AND `reason_code != row.Expected Fail Reason` → row status = `FAKE` (anti-cheat detector `REQ-COMPILER-FAKE-DETECT-001`).
- `result=escaped` → row status = `MISSING` for the negative-control dimension; row's `Release Gate` cannot be `PASS`.
- `result=tripped` AND `reason_code == row.Expected Fail Reason` → negative-control dimension contributes `PASS`.

9. REPLAY CONTRACT
------------------------------------------------------------------------------------------------------------------------
The compiler itself is bound by deterministic replay: identical inputs MUST produce byte-identical output bundles.

Required replay invariants:
- `rule_source_sha256` (sha256 of `00X`)
- `inputs.input_set_fingerprint` (sha256 over sorted list of input file paths + their content hashes)
- `outputs.bundle_sha256` (sha256 of the full report bundle)

Replay receipt:
```
{
  "first_run_compiler_run_id": str,
  "second_run_compiler_run_id": str,
  "rule_source_sha256_match": bool,
  "input_set_fingerprint_match": bool,
  "bundle_sha256_match": bool,
  "match_type": "byte_identical" | "semantic_identical" | "digest_match_only",
  "allowed_nondeterminism": []
}
```

Allowed sources of nondeterminism: only `compiler_run_id`, `started_at_utc`, `finished_at_utc`. Any other field-level diff is a release-blocking nondeterminism.
